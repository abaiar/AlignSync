## 第二章 数据库模块技术解析

### 2.1 数据库连接配置层

#### 2.1.1 配置加载（app/core/config.py）

使用 Pydantic Settings 从 `.env` 文件加载数据库连接串：

```python
class Settings(BaseSettings):
    DATABASE_URL: str = "mysql+aiomysql://root:root@localhost:3306/alignsync"
    model_config = SettingsConfigDict(env_file=".env", env_file_encoding="utf-8", extra="ignore")
```

- **连接串解析**：`mysql+aiomysql://` 表示使用 MySQL 数据库 + aiomysql 异步驱动
- **对应教材**：第3章 SQL 基本概念中的数据库连接；第8章 数据库编程中的编程接口

#### 2.1.2 引擎与会话工厂（app/db/base.py）

```python
engine = create_async_engine(settings.DATABASE_URL, pool_pre_ping=True, future=True)
async_session = async_sessionmaker(engine, class_=AsyncSession, expire_on_commit=False)
Base = declarative_base()

async def get_db() -> AsyncGenerator[AsyncSession, None]:
    async with async_session() as session:
        yield session
```

**技术要点**：
- `pool_pre_ping=True`：每次借出连接前发送 ping，避免使用已断开的连接（对应第11章 故障恢复中的连接可靠性）
- `expire_on_commit=False`：提交后不过期对象，避免重复查询（对应第10章 查询优化，减少不必要的数据库访问）
- `get_db()` 是异步生成器，作为 FastAPI 依赖注入，每个请求一个会话（对应第12章 并发控制中事务隔离的基础）
- `Base = declarative_base()`：所有 ORM 模型的基类，对应第1章 三级模式结构中的"模式"定义

**对应教材**：第1章 数据库系统组成（应用层通过接口连接DBMS）；第11章 事务的基本概念（会话即事务边界）

### 3.1 第1章 绪论 — 数据库系统概述

#### 3.1.1 数据库的4个基本概念

| 概念 | 系统对应 |
|------|---------|
| 数据库（DB） | alignsync 数据库，存储18张表的业务数据 |
| 数据库管理系统（DBMS） | MySQL 8.x，通过 aiomysql 异步驱动连接 |

#### 3.1.2 数据库系统的三级模式结构

教材1.3节定义的三级模式在系统中的对应：

| 模式层级 | 教材定义 | 系统实现 |
|---------|---------|---------|
| 外模式（用户模式） | 数据库用户看见的局部数据逻辑结构 | Pydantic Schemas（[app/schemas/](file:///home/ubuntu/AlignSync/backend/app/schemas/)），如 OrderResponse、CameraListResponse，为不同用户/接口定制视图 |
| 模式（逻辑模式） | 全体数据的逻辑结构 | SQLAlchemy ORM 模型（[app/models/](file:///home/ubuntu/AlignSync/backend/app/models/__init__.py)），定义18张表的字段与关系 |
| 内模式（存储模式） | 数据的物理存储结构 | MySQL InnoDB 引擎的页/区/段存储，由 DBMS 管理 |

**两级映像与数据独立性**：
- 逻辑独立性：外模式/模式映像——修改表结构（如加字段）只需更新 ORM 模型，Pydantic Schema 可独立调整
- 物理独立性：模式/内模式映像——更换存储引擎或调整索引不影响 ORM 模型

### 3.2 第2章 关系模型

#### 3.2.1 关系模型的数据结构

教材2.1节定义关系为元组的集合。系统中每张表即一个关系：

- **关系（表）**：如 `users` 表
- **元组（行）**：每个用户记录
- **属性（列）**：username、password_hash 等
- **域**：如 `status` 字段的取值域为 {"in_stock", "used", "shipped", "returned"}
- **码（主键）**：每张表的 `id` 字段
- **外码（外键）**：如 `users.enterprise_id` → `enterprises.id`

#### 3.2.2 关系的完整性（教材2.3）

**实体完整性（2.3.1）**：主码唯一且非空。
- 系统实现：所有18张表均定义 `id = mapped_column(BigInteger, primary_key=True, autoincrement=True)`
- 代码佐证：[user.py L16](file:///home/ubuntu/AlignSync/backend/app/models/user.py#L16) `id: Mapped[int] = mapped_column(BigInteger, primary_key=True, autoincrement=True)`

**参照完整性（2.3.2）**：外码要么为空，要么引用被参照表中存在的主码。
- 系统实现：通过 `ForeignKey("enterprises.id")` 定义外键约束
- 代码佐证：[user.py L22-24](file:///home/ubuntu/AlignSync/backend/app/models/user.py#L22-L24) `enterprise_id: Mapped[int] = mapped_column(BigInteger, ForeignKey("enterprises.id"), nullable=False)`
- DBMS层面：MySQL InnoDB 自动校验外键约束，违反时拒绝操作

**用户定义完整性（2.3.3）**：针对具体业务定义的约束。
- 系统实现示例：
  - `username` 唯一：`mapped_column(String(100), unique=True, nullable=False)`
  - `order_no` 唯一：`mapped_column(String(50), unique=True, nullable=False)`

### 3.6 第6章 关系数据理论

#### 3.6.1 函数依赖（教材6.2.1）

系统中存在的函数依赖关系：

| 函数依赖 | 说明 |
|---------|------|
| `order_no → order_id` | 订单号唯一确定订单（订单号是候选码） |
| `device_sn → device_id` | 设备序列号唯一确定设备 |
| `username → user_id` | 用户名唯一确定用户 |
| `lock_id → software_lock_id` | 软件锁标识唯一确定软件锁 |
| `order_id, product_id → order_item_id` | 订单ID+产品ID确定明细（在订单内唯一） |
| `enterprise_id → enterprise.type` | 企业ID决定企业类型（传递依赖） |

#### 3.6.2 范式分析

**第一范式（1NF）—— 属性原子性**

所有表的字段都是原子的，不可再分：
- `username` 是字符串，不可拆分
- `price` 是数值，不可拆分
- 例外：`function_list`（JSON数组）、`intrinsics`/`extrinsics`（JSON对象）—— 但这些作为整体使用，在关系模型中视为原子的 JSON 类型（MySQL 原生支持）

**满足1NF**：✅ 全部18张表

**第二范式（2NF）—— 非主属性完全依赖主码**

2NF 要求在1NF基础上，非主属性完全依赖于主码（消除部分依赖）。对于单属性主码的表自动满足。需重点检查复合主码表：

- `user_roles`（主码：user_id + role_id）：只有 user_id 和 role_id 两列，都是主属性，无非主属性 → **满足2NF** ✅
- `role_permissions`（主码：role_id + permission_id）：同理 → **满足2NF** ✅

**满足2NF**：✅ 全部表

**第三范式（3NF）—— 消除非主属性对主码的传递依赖**

3NF 要求在2NF基础上，非主属性不传递依赖于主码。

**分析 order_items 表**：
- 主码：id
- `product_id → product_name, product_model`（产品名称和型号函数依赖于产品ID）
- `order_id → order.enterprise_id`（订单决定企业）

表面上看 `product_name` 通过 `product_id` 依赖，存在传递依赖。**但这是有意为之的反范式设计**（冗余字段），理由：
1. 历史快照：产品改名后，历史订单仍保留原始名称
2. 查询性能：避免每次查询订单都 JOIN products 表
3. 业务需要：订单明细应记录下单时的产品信息

**分析 users 表**：
- `user_id → enterprise_id → enterprise.type`（用户所属企业决定企业类型）
- 存在传递依赖：用户ID → 企业ID → 企业类型
- **解决方案**：不将 enterprise_type 冗余到 users 表，而是在需要时通过 JOIN 查询（如 [order_service.py L25-35](file:///home/ubuntu/AlignSync/backend/app/services/order_service.py#L25-L35)）

**满足3NF**：⚠️ 基本满足，order_items 的冗余字段是有意识的反范式设计

**BCNF —— 消除主属性间的部分依赖**

BCNF 要求在3NF基础上，每个决定因素都包含候选码。

系统中所有表的主码都是单属性 id，且所有函数依赖的左侧都是候选码（id 或 unique 字段），因此 **满足BCNF** ✅

**例外分析**：order_items 中 `product_id → product_name`，product_id 不是 order_items 的候选码，但它引用的是外部表的主码。这种跨表函数依赖不在BCNF考察范围内（BCNF针对单表内依赖）。

#### 3.6.3 模式分解（教材6.4）

系统设计中体现的模式分解原则：

**订单分解**：将"订单"分解为 purchase_orders（订单头）+ order_items（订单明细）
- 分解前：一个订单包含多个商品，若放在一张表会违反2NF
- 分解后：订单头存单次信息，明细存每个商品，通过 order_id 关联
- 保持函数依赖：order_no → order_id 在头表，order_id → 明细信息在明细表

**发货分解**：shipments（发货头）+ shipment_items（发货明细）

**设备BOM分解**：wheel_aligners（设备）+ device_bom（部件清单）

**对应教材**：6.4 保持函数依赖的模式分解——分解后各子模式仍保持原函数依赖。

### 3.11 第11章 数据库恢复技术

#### 3.11.1 事务的基本概念（教材11.1）

- 提交：`await db.commit()` — 所有操作生效
- 回滚：`await db.rollback()` — 所有操作撤销
- 结束：会话关闭

#### 3.11.2 ACID 特性对应

**原子性（Atomicity）**：
- 事务内所有操作要么全做要么全不做
- 系统示例：`register_device` 在一个事务内创建设备+BOM+更新软件锁+更新相机状态（[device_service.py L120-161](file:///home/ubuntu/AlignSync/backend/app/services/device_service.py#L120-L161)），若任何一步失败，整个事务回滚
- 实现：DBMS 的 undo log 保证

**一致性（Consistency）**：
- 事务执行后数据库从一个一致状态变到另一个一致状态
- 系统示例：确认付款时，付款状态变为 confirmed 的同时订单状态变为 paid，两者必须一致（[payment_service.py L263-286](file:///home/ubuntu/AlignSync/backend/app/services/payment_service.py#L263-L286)）
- 实现：应用层业务规则 + DBMS 约束共同保证

**隔离性（Isolation）**：
- 并发事务相互隔离
- 系统：每个请求独立会话（`get_db` 依赖为每个请求创建新会话）
- 实现：DBMS 的锁机制 + MVCC（MySQL InnoDB 默认 RR 隔离级别）

**持久性（Durability）**：
- 事务提交后永久保存
- 系统：`await db.commit()` 后数据落盘
- 实现：DBMS 的 redo log + binlog 保证

#### 3.11.3 故障的种类与恢复（教材11.3-11.5）

**事务故障**：应用程序异常（如 HTTPException）→ `await db.rollback()` 回滚
- 系统示例：[camera_service.py L85-88](file:///home/ubuntu/AlignSync/backend/app/services/camera_service.py#L85-L88) 批量同步失败时回滚

**系统故障**：DBMS 崩溃 → 重启后通过 redo log 恢复已提交事务
- 系统配置：`pool_pre_ping=True` 检测断连

**介质故障**：磁盘损坏 → 需要备份恢复
- 系统提供 init.sql + seed_data.py + alembic 迁移可重建数据库

#### 3.11.4 登记日志文件与检查点（教材11.4-11.6）

- MySQL InnoDB 自动维护 redo log（重做日志）和 undo log（回滚日志）
- binlog 用于主从复制和点恢复
- 系统层面未显式配置，依赖 DBMS 默认机制

### 3.12 第12章 并发控制

#### 3.12.1 事务的隔离级别（教材12.2）

MySQL InnoDB 默认隔离级别：REPEATABLE READ（可重复读）

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---------|------|-----------|------|
| READ UNCOMMITTED | 可能 | 可能 | 可能 |
| READ COMMITTED | 避免 | 可能 | 可能 |
| REPEATABLE READ（默认） | 避免 | 避免 | InnoDB避免 |
| SERIALIZABLE | 避免 | 避免 | 避免 |

系统使用默认 RR 级别，满足大多数业务场景。

#### 3.12.2 封锁协议（教材12.3-12.4）

**系统隐式封锁**：通过 SQLAlchemy 事务，DBMS 自动加锁：
- 共享锁（S锁）：SELECT 操作
- 排他锁（X锁）：INSERT/UPDATE/DELETE 操作

**两段锁协议（教材12.7）**：InnoDB 遵循严格两段锁协议，事务结束时统一释放所有锁。

#### 3.12.3 活锁和死锁（教材12.5）

**活锁**：某些事务长期等待。系统通过合理的查询设计避免（如使用索引快速完成操作）。

**死锁**：多个事务互相等待。系统潜在风险：
- 并发创建订单时，func.max 生成订单号可能产生竞争
- 系统依赖 DBMS 的死锁检测机制（InnoDB 自动检测并回滚代价较小的事务）

#### 3.12.4 批量同步的并发控制（教材12.9）

[camera_service.py](file:///home/ubuntu/AlignSync/backend/app/services/camera_service.py) 的 `batch_sync` 采用逐条提交+回滚策略：

```python
for item in req.cameras:
    try:
        await sync_camera(db, item, user)  # 内部commit
        success_count += 1
    except HTTPException as e:
        await db.rollback()  # 回滚当前失败项
        fail_count += 1      # 继续下一条
```

这是一种**乐观并发控制**的变体——逐条尝试，失败回滚不影响其他。对应教材12.9 其他并发控制机制。

## 第四章 数据库设计决策合理性分析

### 4.1 主键选型：BigInteger 自增 vs UUID

**设计决策**：所有表使用 `BigInteger` 自增主键。

**合理性分析**：

| 维度 | BigInteger 自增 | UUID |
|------|----------------|------|
| 存储空间 | 8字节 | 16字节（128位） |
| 索引性能 | 顺序写入，B+树插入高效 | 随机写入，B+树页分裂多 |
| 可读性 | 1, 2, 3... 直观 | 550e8400-e29b... 难读 |
| 分布式 | 不适合分库分表 | 天然适合 |
| 安全性 | 可猜测ID | 不可猜测 |

**结论**：系统为单机/小规模应用，自增主键在存储、性能、可读性上均优于UUID。BigInteger（64位）支持约 9.2×10^18 条记录，完全满足需求。

**对应教材**：第7章 物理结构设计——选择关系模式存取方法。

### 4.2 冗余字段设计：order_items 中的 product_name/product_model

**设计决策**：order_items 同时存储 product_id（外键）和 product_name、product_model（冗余）。

**合理性分析**：

1. **历史快照需求**：产品可能改名或下架，历史订单应记录下单时的产品名称。若仅存 product_id 外键，产品改名后历史订单显示新名称，不符合业务逻辑。
2. **查询性能**：避免每次查询订单明细都 JOIN products 表，减少 I/O。
3. **反范式权衡**：违反3NF（product_id → product_name 存在传递依赖），但换取了历史准确性和查询性能。

**教材对应**：第6章 范式理论中"适度反范式"的实践——在满足业务需求的前提下，允许局部违反范式以提升性能。

### 4.3 JSON 字段使用：相机标定数据与功能版本

**设计决策**：
- cameras.intrinsics / cameras.extrinsics 使用 JSON 类型
- products.function_versions / software_locks.function_list 使用 JSON 类型

**合理性分析**：

| 维度 | JSON | 关系表 |
|------|------|--------|
| 结构灵活性 | 高（可存任意结构） | 低（需固定列） |
| 查询能力 | MySQL支持JSON路径查询 | 标准SQL |
| 数据完整性 | 应用层校验 | DBMS约束 |
| 适用场景 | 半结构化、整体读写 | 结构化、需独立查询 |

**相机标定数据**（intrinsics/extrinsics）：包含矩阵、畸变系数等嵌套结构，且总是整体读写，JSON 最合适。若拆为关系表需多张表，增加复杂度。

**功能版本列表**（function_versions/function_list）：简单数组，JSON 简洁高效。

**教材对应**：第1章 数据模型——数据库领域中不断涌现的数据模型（JSON文档模型）。

### 4.4 外键约束与级联策略

**设计决策**：所有外键使用默认策略（RESTRICT），未设置 ON DELETE CASCADE / SET NULL。

**合理性分析**：

1. **数据安全**：避免误删被引用记录导致级联数据丢失
2. **业务可控**：删除操作由应用层显式校验依赖关系后执行
3. **符合业务**：企业、用户、订单等核心数据不应因外键级联而被意外删除

**教材对应**：第5章 参照完整性——违约处理策略选择。

### 4.5 循环依赖处理：software_locks ↔ wheel_aligners

**设计问题**：
- wheel_aligners.software_lock_id → software_locks.id（设备绑定软件锁）
- software_locks.bound_device_id → wheel_aligners.id（软件锁绑定设备）

两者互相引用，形成循环依赖，无法在建表时同时创建外键。

**解决方案**（[initial_schema.py L141-192](file:///home/ubuntu/AlignSync/backend/alembic/versions/e90b5ee4edc0_initial_schema.py#L141-L192)）：
1. 先建 software_locks 表，bound_device_id 列暂不加外键约束
2. 再建 wheel_aligners 表，software_lock_id 正常加外键（指向已存在的 software_locks）
3. 用 `op.create_foreign_key(...)` 通过 ALTER TABLE 补上 software_locks.bound_device_id 的外键

**合理性**：
- 物理上打破建表顺序的循环
- 逻辑上保持双向引用的语义完整性
- 迁移脚本可回溯（downgrade 先删外键再删表）

**教材对应**：第7章 逻辑结构设计——E-R图转换中的循环联系处理。

### 4.6 RBAC 多对多建模

**设计决策**：通过 user_roles 和 role_permissions 两张关联表实现三级授权。

**合理性分析**：

1. **标准化 RBAC 模型**：用户↔角色↔权限是经典 RBAC 标准（NIST RBAC）
2. **灵活性**：角色可动态调整权限，用户可拥有多角色，无需改代码
3. **关联表设计**：复合主键 (user_id, role_id) / (role_id, permission_id)，避免冗余ID列
4. **查询效率**：通过 JOIN 查询用户权限，3张表连接即可获取用户全部权限码

**替代方案对比**：
- 直接在 users 表加 permissions 字段（JSON）：违反1NF，无法精细管理
- 单一角色（1:N）：灵活性不足，用户可能需要多角色

**教材对应**：第4章 数据库安全性控制——自主存取控制方法与数据库角色。

### 4.7 状态机字段设计

**设计决策**：使用 String 类型存储状态枚举（如 "draft"、"pending"、"confirmed"），而非数据库原生 ENUM 或独立状态表。

**合理性分析**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| String（系统采用） | 灵活、可读、无需改表结构 | 无DBMS级约束 |
| ENUM | DBMS级约束 | 修改需ALTER TABLE |
| 状态表+外键 | 标准化、可扩展 | 增加JOIN复杂度 |

**系统的选择理由**：
1. 状态值较多且可能扩展（如 purchase_orders 有8个状态）
2. 应用层通过 if-else 校验状态转换，比DBMS约束更灵活
3. 字符串状态可读性强，调试方便
4. MySQL ENUM 修改需 ALTER TABLE，影响生产可用性

**状态机示例**（purchase_orders.status）：
```
draft → pending → confirmed → awaiting_payment → paid → shipped → completed
                → rejected
```

**教材对应**：第5章 用户定义完整性——状态约束在应用层实现。

## 第五章 数据库相关问题与解决方案

### 5.1 异步 ORM 的事务管理

**问题现象**：传统同步 SQLAlchemy 的事务管理（`session.commit()`）不适用于 FastAPI 异步框架，需要异步事务管理。

**课程理论依据**：第11章 事务的基本概念——事务是操作序列的不可分割工作单位；第8章 数据库编程——通过高级语言实现复杂应用。

**解决方案**：
- 使用 `sqlalchemy.ext.asyncio.AsyncSession` 替代同步 Session
- 通过 `async_sessionmaker` 创建会话工厂
- `get_db()` 异步生成器作为 FastAPI 依赖，每个请求独立会话
- `await db.commit()` / `await db.rollback()` 异步提交/回滚

**代码实现**（[app/db/base.py](file:///home/ubuntu/AlignSync/backend/app/db/base.py)）：
```python
async_session = async_sessionmaker(engine, class_=AsyncSession, expire_on_commit=False)

async def get_db() -> AsyncGenerator[AsyncSession, None]:
    async with async_session() as session:
        yield session
```

**关键配置**：`expire_on_commit=False` 避免提交后访问对象属性触发额外查询（性能优化）。

### 5.2 N+1 查询问题与 selectinload 解决

**问题现象**：查询订单列表时，若不预加载明细，每个订单访问 `.items` 属性会触发一次单独查询。N个订单导致 N+1 次数据库查询，严重影响性能。

**课程理论依据**：第10章 查询优化——代数优化与物理优化；第3章 连接查询。

**解决方案**：使用 `selectinload` 预加载关联：
```python
select(PurchaseOrder).options(selectinload(PurchaseOrder.items))  # order_service.py L193
```

**原理**：`selectinload` 在主查询完成后，用一次 `WHERE id IN (...)` 查询加载所有关联记录，将 N+1 次查询降为 2 次。

**系统中的应用位置**：
- [order_service.py L137-141](file:///home/ubuntu/AlignSync/backend/app/services/order_service.py#L137-L141)：创建订单后重载
- [shipment_service.py L55-59](file:///home/ubuntu/AlignSync/backend/app/services/shipment_service.py#L55-L59)：发货查询
- [device_service.py L164-168](file:///home/ubuntu/AlignSync/backend/app/services/device_service.py#L164-L168)：设备查询

### 5.3 循环外键依赖与 ALTER TABLE 处理

**问题现象**：software_locks.bound_device_id 和 wheel_aligners.software_lock_id 互相引用，建表时无法同时创建外键（被引用表必须先存在）。

**课程理论依据**：第3章 数据定义——基本表的定义与修改；第7章 逻辑结构设计。

**解决方案**（[initial_schema.py L141-192](file:///home/ubuntu/AlignSync/backend/alembic/versions/e90b5ee4edc0_initial_schema.py#L141-L192)）：
1. 建 software_locks 表时，bound_device_id 列存在但不加外键约束
2. 建 wheel_aligners 表，software_lock_id 外键指向已存在的 software_locks
3. 用 `op.create_foreign_key()` 通过 ALTER TABLE 补上 software_locks.bound_device_id 外键

**代码实现**：
```python
# 步骤1：建 software_locks（bound_device_id 无外键）
op.create_table('software_locks', sa.Column('bound_device_id', sa.BigInteger(), nullable=True), ...)
# 步骤2：建 wheel_aligners（software_lock_id 有外键）
op.create_table('wheel_aligners', sa.Column('software_lock_id', sa.BigInteger(),
    sa.ForeignKeyConstraint(['software_lock_id'], ['software_locks.id'])), ...)
# 步骤3：ALTER TABLE 补外键
op.create_foreign_key('fk_software_locks_bound_device_id_wheel_aligners',
    'software_locks', 'wheel_aligners', ['bound_device_id'], ['id'])
```

**回滚处理**：downgrade() 中先 drop wheel_aligners 再 drop software_locks，顺序正确。

### 5.4 并发订单号生成与 func.max 方案

**问题现象**：多用户并发创建订单时，若使用"查询最大序号+1"的方式生成订单号，可能产生重复订单号。

**课程理论依据**：第12章 并发控制——并发调度的可串行性；第6章 函数依赖。

**当前方案**（[order_service.py L38-54](file:///home/ubuntu/AlignSync/backend/app/services/order_service.py#L38-L54)）：
```python
prefix = "PO" + datetime.now().strftime("%Y%m%d")
result = await db.execute(
    select(func.max(PurchaseOrder.order_no)).where(PurchaseOrder.order_no.like(prefix + "%"))
)
max_no = result.scalar_one_or_none()
seq = int(max_no[-4:]) + 1 if max_no else 1
return f"{prefix}{seq:04d}"
```

**并发风险分析**：
- 两个事务同时查询到相同的 max_no，生成相同序号
- UNIQUE 约束会阻止第二个 INSERT，但事务失败

**缓解措施**：
1. order_no 的 UNIQUE 约束保证最终一致性（重复时DBMS拒绝）
2. RR 隔离级别下，SELECT ... FOR UPDATE 可加锁（系统未显式使用）
3. 单机小规模场景下并发冲突概率低

**改进方向**（答辩可提及）：
- 使用数据库序列（SEQUENCE）
- 使用 Redis 分布式计数器
- 使用 UUID 替代流水号

**教材对应**：第12章 并发控制——并发调度可串行性。

### 5.5 数据隔离与视图机制

**问题现象**：manufacturer 用户不应看到其他企业的数据，需要在所有查询中强制添加企业过滤。

**课程理论依据**：第4章 视图机制——视图隐藏数据；第3章 数据查询——选择运算。

**解决方案**：在服务层根据用户企业类型动态添加 WHERE 条件：

```python
# order_service.py L191-200
ent_type = await _get_enterprise_type(db, user)
if ent_type == "manufacturer":
    stmt = stmt.where(PurchaseOrder.enterprise_id == user.enterprise_id)
    count_stmt = count_stmt.where(PurchaseOrder.enterprise_id == user.enterprise_id)
```

**应用场景**：
- 订单列表：manufacturer 只见本企业订单
- 发货单列表：manufacturer 只见发给本企业的发货单
- 相机列表：manufacturer 只见本企业相机
- 统计数据：manufacturer 只统计本企业数据

```sql
-- 等价于为每个manufacturer企业创建视图
CREATE VIEW manufacturer_orders AS

```

系统在应用层实现"行级视图"，比数据库视图更灵活（可动态参数化）。

### 5.6 批量同步的逐条回滚策略

**问题现象**：批量同步100个相机时，若第50个失败，前49个已成功的数据应保留，不应全部回滚。

**课程理论依据**：第12章 并发控制——其他并发控制机制；第11章 事务恢复策略。

**解决方案**（[camera_service.py L67-102](file:///home/ubuntu/AlignSync/backend/app/services/camera_service.py#L67-L102)）：
```python
for item in req.cameras:
    try:
        await sync_camera(db, item, user)  # 内部commit
        success_count += 1
    except HTTPException as e:
        await db.rollback()  # 回滚当前失败项的未提交变更
        fail_count += 1      # 记录失败，继续下一条
    except Exception as e:
        await db.rollback()
        fail_count += 1
```

**策略分析**：
- 每条记录独立提交（sync_camera 内部 `await db.commit()`）
- 失败时回滚当前会话的未提交变更
- 继续处理下一条，保证部分成功

**权衡**：
- 优点：最大化成功率，单个失败不影响其他
- 缺点：每条独立提交，性能较低（可改进为批量提交）
- 适用场景：批量导入对部分失败容忍度高

**教材对应**：第12章 其他并发控制机制——多版本并发控制的思想变体。

### A. 理论映射类问答

**Q1：你的系统用的是什么数据模型？为什么选择关系模型？**

答：系统采用关系数据模型（教材第1章2.6节），基于 MySQL 关系数据库管理系统。选择理由：(1) 数据结构规范，业务实体间关系明确（企业-用户-订单-发货等），适合表格化表达；(2) 事务支持完善，InnoDB 引擎保证 ACID 特性；(3) SQL 标准化，生态成熟。代码佐证：[app/models/](file:///home/ubuntu/AlignSync/backend/app/models/__init__.py) 中18张表均为关系模型，通过 SQLAlchemy ORM 映射。

**Q2：系统中如何体现关系的三类完整性？**

答：(1) 实体完整性——所有表主键 `id` 非空唯一（[user.py L16](file:///home/ubuntu/AlignSync/backend/app/models/user.py#L16)）；(2) 参照完整性——外键约束如 `ForeignKey("enterprises.id")`，DBMS自动校验（[user.py L22-24](file:///home/ubuntu/AlignSync/backend/app/models/user.py#L22-L24)）；(3) 用户定义完整性——如 `username` UNIQUE、`price` Numeric(12,2)、`is_active` default=True，业务规则如 BR-FIN-001 在应用层校验（[payment_service.py L94-98](file:///home/ubuntu/AlignSync/backend/app/services/payment_service.py#L94-L98)）。对应教材第2章2.3节。

**Q3：系统满足第几范式？请举例说明。**

答：系统满足 BCNF。以 order_items 为例：主码为 id，非主属性 product_name、quantity 等完全依赖于 id（满足2NF），无非主属性传递依赖（满足3NF），所有决定因素均为候选码（满足BCNF）。注意 product_name 是有意冗余的反范式设计，用于历史快照。对应教材第6章6.2节。详见 [第四章 4.2](#42-冗余字段设计order_items-中的-product_nameproduct_model)。

**Q4：系统中哪里用到了连接查询？**

答：权限查询是典型三表连接：`permissions JOIN role_permissions JOIN user_roles`，获取用户所有权限码。代码在 [deps.py L37-43](file:///home/ubuntu/AlignSync/backend/app/api/deps.py#L37-L43)。统计服务中 `OrderItem JOIN PurchaseOrder` 按产品汇总销售额（[statistics_service.py L203-211](file:///home/ubuntu/AlignSync/backend/app/services/statistics_service.py#L203-L211)）。对应教材第3章3.3.2 连接查询。

**Q5：事务的 ACID 特性在系统中如何体现？**

答：(1) 原子性——register_device 事务内创建设备+BOM+更新锁+更新相机，要么全成功要么全回滚（[device_service.py L120-161](file:///home/ubuntu/AlignSync/backend/app/services/device_service.py#L120-L161)）；(2) 一致性——confirm_payment 同时更新付款状态和订单状态（[payment_service.py L263-286](file:///home/ubuntu/AlignSync/backend/app/services/payment_service.py#L263-L286)）；(3) 隔离性——每请求独立会话；(4) 持久性——commit 后数据落盘。对应教材第11章。

**Q6：系统如何实现数据库安全性控制？**

答：(1) 身份鉴别——JWT+用户名密码（[auth.py](file:///home/ubuntu/AlignSync/backend/app/api/routers/auth.py)）；(2) 存取控制——RBAC 三级模型用户→角色→权限（[deps.py L57-69](file:///home/ubuntu/AlignSync/backend/app/api/deps.py#L57-L69)）；(3) 视图机制——数据隔离，manufacturer 只见本企业数据（[order_service.py L196-200](file:///home/ubuntu/AlignSync/backend/app/services/order_service.py#L196-L200)）。对应教材第4章。

### B. 设计权衡类问答

**Q7：为什么用 BigInteger 自增主键而不是 UUID？**

答：系统为单机应用，自增主键在存储空间（8字节 vs 16字节）、索引性能（顺序写入无页分裂）、可读性上均优于UUID。BigInteger 64位支持约 9.2×10^18 条记录。若未来需要分布式分库，可迁移到雪花算法。详见 [第四章 4.1](#41-主键选型biginteger-自增-vs-uuid)。

**Q8：order_items 为什么同时存 product_id 和 product_name？这不是违反范式吗？**

答：这是有意识的反范式设计（违反3NF），理由：(1) 历史快照——产品改名后历史订单保留原始名称；(2) 查询性能——避免每次 JOIN products 表；(3) 业务需要——订单明细应记录下单时产品信息。属于教材第6章"适度反范式"的工程实践。详见 [第四章 4.2](#42-冗余字段设计order_items-中的-product_nameproduct_model)。

**Q9：为什么相机标定数据用 JSON 而不是拆成多张表？**

答：相机内参/外参是嵌套结构（矩阵+畸变系数），且总是整体读写、不需独立查询某个分量。JSON 类型在 MySQL 中原生支持，兼顾灵活性与性能。若拆为关系表需多张表增加 JOIN 复杂度，收益低。对应教材第1章"不断涌现的数据模型"。详见 [第四章 4.3](#43-json-字段使用相机标定数据与功能版本)。

**Q10：software_locks 和 wheel_aligners 互相引用，建表时怎么处理？**

答：循环外键通过 ALTER TABLE 延迟创建解决：先建 software_locks（bound_device_id 无外键），再建 wheel_aligners（software_lock_id 有外键指向 software_locks），最后用 `op.create_foreign_key()` 补上 software_locks.bound_device_id 外键。代码在 [initial_schema.py L185-192](file:///home/ubuntu/AlignSync/backend/alembic/versions/e90b5ee4edc0_initial_schema.py#L185-L192)。详见 [第四章 4.5](#45-循环依赖处理software_locks--wheel_aligners)。

**Q11：为什么用字符串存状态而不是 ENUM？**

答：String 类型比 ENUM 更灵活——状态值扩展时无需 ALTER TABLE（ENUM 修改影响生产可用性），应用层通过状态机校验转换更易维护。MySQL ENUM 修改需重建表，风险高。对应教材第5章用户定义完整性。详见 [第四章 4.7](#47-状态机字段设计)。

**Q12：外键为什么不用 ON DELETE CASCADE？**

答：默认 RESTRICT 策略避免误删被引用记录导致级联数据丢失。企业、用户、订单等核心数据不应因外键级联被意外删除。删除操作由应用层显式校验依赖关系后执行，更安全可控。对应教材第5章参照完整性违约处理。

### C. 扩展性与安全性类问答

**Q13：系统如何优化查询性能？**

答：(1) selectinload 预加载避免 N+1 查询（[order_service.py L193](file:///home/ubuntu/AlignSync/backend/app/services/order_service.py#L193)）；(2) 批量预取用 IN 查询替代循环单查（[order_service.py L79-82](file:///home/ubuntu/AlignSync/backend/app/services/order_service.py#L79-L82)）；(3) 聚合计算下推数据库（func.count/sum/group_by）；(4) 唯一约束自动创建索引加速等值查询；(5) `expire_on_commit=False` 避免提交后重复查询。对应教材第10章查询优化。

**Q14：并发创建订单时订单号会重复吗？**

答：当前用 `func.max` 查询当日最大序号+1 生成订单号（[order_service.py L38-54](file:///home/ubuntu/AlignSync/backend/app/services/order_service.py#L38-L54)），理论上存在并发冲突风险。但 order_no 有 UNIQUE 约束，DBMS 会拒绝重复插入保证最终一致性。改进方向：使用数据库序列、Redis 计数器或雪花算法。对应教材第12章并发控制。详见 [第五章 5.4](#54-并发订单号生成与-funcmax-方案)。

**Q15：系统的事务隔离级别是什么？够用吗？**

答：MySQL InnoDB 默认 REPEATABLE READ（可重复读），在该级别下 InnoDB 通过 Next-Key Locking 解决幻读问题。系统为典型的 OLTP 业务，RR 级别满足需求。若需更高一致性可升级到 SERIALIZABLE，但会降低并发性能。对应教材第12章12.2节。

**Q16：如何保证 manufacturer 看不到其他企业数据？**

答：在服务层根据用户企业类型动态添加 WHERE 过滤，相当于应用层行级视图。如 [order_service.py L196-200](file:///home/ubuntu/AlignSync/backend/app/services/order_service.py#L196-L200) 中 manufacturer 只查询 `enterprise_id == user.enterprise_id` 的订单。这种方案比数据库视图更灵活（可动态参数化），但要求开发者在每个查询中严格遵守。对应教材第4章视图机制。详见 [第五章 5.5](#55-数据隔离与视图机制)。

**Q17：数据库模式如何演进和版本管理？**

答：使用 Alembic 迁移工具管理数据库模式版本。初始迁移 `e90b5ee4edc0` 创建全部18张表（[initial_schema.py](file:///home/ubuntu/AlignSync/backend/alembic/versions/e90b5ee4edc0_initial_schema.py)）。每次 schema 变更生成新迁移脚本，通过 `alembic upgrade head` / `alembic downgrade -1` 进行版本切换。`alembic/env.py` 配置异步迁移环境，`target_metadata = Base.metadata` 关联 ORM 模型支持 autogenerate。对应教材第7章数据库实施与维护。

**Q18：如果数据库宕机，系统能恢复吗？**

答：(1) 事务故障——应用异常时 `await db.rollback()` 回滚（[camera_service.py L85-88](file:///home/ubuntu/AlignSync/backend/app/services/camera_service.py#L85-L88)）；(2) 系统故障——InnoDB 通过 redo log 恢复已提交事务，undo log 回滚未提交事务，`pool_pre_ping=True` 自动检测断连；(3) 介质故障——可通过 init.sql + alembic 迁移 + seed_data.py 重建数据库。对应教材第11章恢复技术。

**Q19：批量同步100个相机，第50个失败怎么办？**

答：采用逐条提交+回滚策略：sync_camera 内部 commit，失败时 rollback 当前事务并继续下一条（[camera_service.py L77-95](file:///home/ubuntu/AlignSync/backend/app/services/camera_service.py#L77-L95)）。返回结果含 success_count 和 fail_count，调用方可了解每条结果。这种乐观策略最大化成功率，适合对部分失败容忍度高的批量导入场景。对应教材第12章其他并发控制机制。详见 [第五章 5.6](#56-批量同步的逐条回滚策略)。

**Q20：系统用了哪些索引？如何设计的？**

答：(1) 主键聚簇索引——所有表的 id，InnoDB 自动创建；(2) 唯一辅助索引——username、order_no、device_sn、sn、lock_id、ticket_no、code 等高频查询字段，通过 `unique=True` 隐式创建；(3) 外键自动索引——InnoDB 为外键自动创建索引加速 JOIN。索引设计原则：对等值查询频率高、区分度高的字段建索引。对应教材第9章索引结构。
