## 一、项目背景与功能概述

### 1.1 系统定位与业务背景

各位老师好，我是本课程设计的负责人。我所做的项目叫 **AlignSync 车轮定位仪生产协同管理系统**。在车轮定位仪这个行业中，一台完整的定位仪整机并不是一家企业独立完成的，而是要由两家企业协同配合：

- **智核科技有限公司**（核心技术企业）：负责生产核心零部件，包括工业相机的组装与标定、定位仪软件的开发以及软件锁的授权管理。
- **精工定位仪制造厂**（生产厂）：向核心技术企业采购相机与软件锁，组装成整机、完成授权验证并对外销售，还要负责售后追溯。

这两个企业之间存在大量数据交互：相机标定数据要同步到系统、软件锁授权要同步并绑定到生产厂、采购订单要在两家企业之间流转、发货收货要互相确认、组装后的整机要建立 BOM 追溯链条、售后工单也要在两家企业之间处理。**我设计这个系统的核心目标就是把这两家企业的业务流程在数据库层面打通，形成一个闭环的协同平台**。

### 1.4 数据库在系统中的角色

我在设计时，把数据库定位为系统的"四个核心"：

1. **数据持久化中心**：所有业务数据（企业、用户、相机、软件锁、订单、付款、发货、设备、售后）的单一可信来源（SSOT）。
2. **业务约束载体**：通过外键、唯一约束、CHECK、NOT NULL 等约束在数据库层强制业务规则，即使应用层出错也能保证数据一致性。
3. **追溯链条基础**：通过 device_bom、shipment_items 等关联表，建立从整机 → 部件 → 订单 → 发货的完整逆向追溯链条，对应 BR-QRY-001。
4. **协同流程状态机**：通过 status 字段在订单/付款/发货/设备/售后等表上的状态流转，驱动两家企业的业务协同。

## 二、数据库设计思路（四阶段，对应教材第7章）

### 2.1 需求分析（对应教材 7.2）

#### 2.1.1 数据字典

按照教材 7.2.3 节"数据字典"的要求，我整理了 4 类数据字典内容：

### 2.2 概念结构设计（E-R 模型，对应教材 7.3）

按照教材 7.3.2 节"E-R 模型"，我抽象出以下实体：

#### 2.2.1 核心实体（8 个）

1. **企业（enterprises）**：参与协同的两家企业。
2. **用户（users）**：隶属于企业的操作人员。
3. **角色（roles）**：业务岗位抽象。
4. **权限（permissions）**：可执行的操作。
5. **产品（products）**：相机与软件锁的产品目录。
6. **相机（cameras）**：物理实体，含标定数据。
7. **软件锁（software_locks）**：授权凭证。
8. **定位仪设备（wheel_aligners）**：整机。

#### 2.2.2 业务实体

订单（purchase_orders）、订单明细（order_items）、付款（payments）、发货单（shipments）、发货明细（shipment_items）、设备 BOM（device_bom）、售后工单（after_sales_tickets）、通知（notifications）。

#### 2.2.3 实体间关系

- 1:N —— 企业 1:N 用户；企业 1:N 相机/软件锁/定位仪/订单。
- M:N —— 用户 M:N 角色（通过 user_roles）；角色 M:N 权限（通过 role_permissions）。
- 1:1 —— 软件锁 1:1 定位仪设备（绑定关系，循环外键）。

#### 2.2.4 E-R 图设计要点

我在 E-R 图设计时遵循教材 7.3.5 节"用 E-R 图进行概念结构设计"的原则：

1. **实体先于关系**：先识别 8 个核心实体，再识别关系实体（订单、付款、发货等）。
2. **冗余属性归并到关系实体**：比如订单明细的 `product_name / product_model` 作为冗余快照，挂在 `order_items` 上而非 `products` 上。
3. **复合属性用 JSON 表示**：相机内参（fx/fy/cx/cy/distortion）、外参（rotation/translation）、软件功能列表（function_list）作为整体存储，对应教材 7.3.2 节"复合属性"。
4. **多值属性用关联表表示**：用户多角色、角色多权限都通过关联表实现。

### 2.3 逻辑结构设计（对应教材 7.4）

#### 2.3.1 E-R 图向关系模型转换

按照教材 7.4.1 节"E-R 图向关系模型的转换"规则：

- **1:1 关系**：将外键放在任意一方。例如 `software_locks` ↔ `wheel_aligners` 的绑定关系：`wheel_aligners.software_lock_id` 指向 `software_locks.id`，`software_locks.bound_device_id` 反向指向 `wheel_aligners.id`（双向引用，循环外键）。
- **1:N 关系**：将外键放在 N 的一方。例如 `users.enterprise_id` → `enterprises.id`、`cameras.enterprise_id` → `enterprises.id`、`order_items.order_id` → `purchase_orders.id`。
- **M:N 关系**：必须建立关联表。例如 `user_roles(user_id, role_id)`、`role_permissions(role_id, permission_id)`，主键为复合主键。

#### 2.3.3 范式优化（1NF → 2NF → 3NF → BCNF）

按照教材第 6 章 6.2 节"规范化"的范式理论，逐表分析：

- **1NF（原子性）**：所有表的字段都是原子的。需要特别说明的是 `cameras.intrinsics / extrinsics` 和 `software_locks.function_list` 用 JSON 存储，看似违反 1NF，但 MySQL 8.0 的 JSON 类型本质上是结构化文档存储，逻辑上仍是一个不可分割的"标定参数包"整体，类似教材中"复合属性"的处理方式，可以视为满足 1NF。
- **2NF（消除部分函数依赖）**：所有非主属性对主码完全依赖。`user_roles` 和 `role_permissions` 用复合主键（user_id, role_id）和（role_id, permission_id），不存在非主属性部分依赖主码的情况。
- **3NF（消除传递函数依赖）**：所有非主属性不传递依赖于主码。例如 `users` 表中 `enterprise_id` 直接外键引用 `enterprises.id`，而不在 `users` 表中冗余企业名称（避免企业改名时多表同步）。
- **BCNF（消除主属性对候选码的部分/传递依赖）**：18 张表都满足 BCNF。每个决定因素都是候选码。
- **反范式权衡（重点）**：`order_items.product_name` 和 `order_items.product_model` 是冗余字段（产品名称和型号已存在于 `products` 表），看起来违反 3NF，但这是我**有意为之的反范式设计**。理由是：(1) **历史快照需求**——产品名称/型号可能被修改，但订单创建时的产品信息必须冻结；(2) **查询性能**——订单详情查询是高频操作，避免每次 JOIN products 表；(3) **业务隔离**——订单明细即使引用的 product 被删除（软删除），仍能展示历史信息。这是典型的"读多写少 + 历史快照"场景下的反范式权衡。

### 2.4 物理结构设计（对应教材 7.5）

按照教材 7.5 节"数据库的物理结构设计"，我从以下方面进行了物理设计：

#### 2.4.1 存储引擎选型

我选择 **InnoDB** 作为所有表的存储引擎。理由：
- **支持事务**（ACID），满足订单/付款等关键业务的原子性要求（对应教材第 11 章事务）。
- **支持外键约束**，能在数据库层强制参照完整性（对应教材第 5 章 5.3 节参照完整性）。
- **行级锁**，支持高并发而不阻塞整表（对应教材第 12 章封锁协议）。
- **支持崩溃恢复**，通过 redo log 保证持久性。

所有表均显式声明 `ENGINE=InnoDB`（参见 [SQL 第 76 行](file:///home/ubuntu/AlignSync/能够生成整个项目的数据库的SQL语句.sql#L76) 等多处）。

#### 2.4.2 字符集选型

我选择 **utf8mb4** 字符集 + **utf8mb4_unicode_ci** 排序规则（参见 [SQL 第 17 行](file:///home/ubuntu/AlignSync/能够生成整个项目的数据库的SQL语句.sql#L17)）。理由：
- 完整支持 Unicode（包括中文、emoji）。
- utf8mb4_unicode_ci 在多语言排序上更准确。
- 建库时统一设置，避免每张表重复声明（虽然我也在每张表上重复声明以便独立部署）。

#### 2.4.3 字段类型选型

| 字段类型 | 应用场景 | 选型理由 |
| --- | --- | --- |
| `BIGINT AUTO_INCREMENT` | 所有主键 | 64 位整数，支撑 9.2×10^18 行；自增便于插入 |
| `VARCHAR(n)` | 名称、编号、状态等 | 变长字符串，节省空间 |
| `DECIMAL(12,2)` | 金额字段（如 total_amount、unit_price、amount） | 精确小数，避免 FLOAT 浮点误差；12 位整数 + 2 位小数可表示最大 99 亿金额 |
| `JSON` | 标定数据（intrinsics/extrinsics）、功能列表（function_list） | 结构化文档存储，便于扩展 |
| `DATETIME` | 时间字段（created_at、updated_at、assembled_at 等） | 范围广（1000-9999 年），不受时区影响 |
| `TEXT` | 长文本（description、remark、resolution、rejected_reason） | 大文本存储 |
| `TINYINT(1)` | 布尔字段（is_active、is_read） | MySQL 中等价于 BOOL |

#### 2.4.4 索引设计

按照教材第 9 章 9.2 节"索引结构"和第 7 章 7.5.2 节"选择关系模式存取方法"，我设计了三类索引（详见 [SQL 第 420-491 行](file:///home/ubuntu/AlignSync/能够生成整个项目的数据库的SQL语句.sql#L420)）：

1. **主键索引（PRIMARY KEY）**：自动创建聚簇索引，每张表必建。
2. **唯一索引（UNIQUE）**：业务唯一性约束，如 `uk_cameras_sn`、`uk_users_username`、`uk_purchase_orders_order_no` 等。
3. **外键列索引**：所有外键字段都建索引（MySQL 自动不建，需手动 CREATE INDEX），如 `idx_users_enterprise_id`、`idx_order_items_order_id` 等，加速 JOIN 操作。
4. **业务高频查询列索引**：如 `idx_cameras_status`（按状态查库存）、`idx_purchase_orders_status`（按状态查待办）、`idx_shipments_tracking_no`（按物流单号查发货）、`idx_after_sales_tickets_status`（按状态查工单）等。

### 3.2 实体关系详解

#### 3.2.1 enterprises 1:N users（一个企业多个用户）

- **基数**：1 端最小 0 最大 1；N 端最小 0 最大 N。
- **参与约束**：enterprises 端全参与（必须有企业才有用户）；users 端部分参与（企业可以暂时没有用户）。
- **外键实现**：`users.enterprise_id BIGINT NOT NULL`，外键 `fk_users_enterprise_id`（参见 [SQL 第 141 行](file:///home/ubuntu/AlignSync/能够生成整个项目的数据库的SQL语句.sql#L141)）。

#### 3.2.2 users M:N roles（通过 user_roles）

- **基数**：双向多对多，一个用户可有多角色，一个角色可属于多用户。
- **参与约束**：两端均部分参与。
- **外键实现**：`user_roles` 关联表，复合主键 `(user_id, role_id)`，分别外键到 users 和 roles（参见 [SQL 第 147-153 行](file:///home/ubuntu/AlignSync/能够生成整个项目的数据库的SQL语句.sql#L147)）。

#### 3.2.3 roles M:N permissions（通过 role_permissions）

- **基数**：双向多对多。
- **参与约束**：两端均部分参与。
- **外键实现**：`role_permissions` 关联表，复合主键 `(role_id, permission_id)`（参见 [SQL 第 158-164 行](file:///home/ubuntu/AlignSync/能够生成整个项目的数据库的SQL语句.sql#L158)）。

#### 3.2.4 enterprises 1:N cameras / software_locks / wheel_aligners / purchase_orders

- **基数**：1 端 1，N 端 N。
- **参与约束**：enterprises 端全参与；另一端部分参与（企业可以暂时没有相机/订单）。
- **外键实现**：分别在 `cameras.enterprise_id`、`software_locks.bound_enterprise_id`、`wheel_aligners.enterprise_id`、`purchase_orders.enterprise_id` 上声明外键。

#### 3.2.5 purchase_orders 1:N order_items；order_items N:1 products

- **基数**：1 端订单，N 端明细。
- **外键实现**：`order_items.order_id` → `purchase_orders.id`，`order_items.product_id` → `products.id`（参见 [SQL 第 282-283 行](file:///home/ubuntu/AlignSync/能够生成整个项目的数据库的SQL语句.sql#L282)）。

#### 3.2.7 shipments 1:N shipment_items

  - `software_locks.bound_device_id` → `wheel_aligners.id`（建表后用 ALTER 补充，参见 [SQL 第 236-238 行](file:///home/ubuntu/AlignSync/能够生成整个项目的数据库的SQL语句.sql#L236)）。

## 五、数据库设计亮点与创新点

### 5.1 循环外键延迟约束（software_locks ↔ wheel_aligners）

软件锁与定位仪设备是 1:1 双向绑定关系：`wheel_aligners.software_lock_id` 指向软件锁，`software_locks.bound_device_id` 反向指向设备。由于 MySQL 建表时要求被引用表必须先存在，所以我先建 `software_locks` 表（不带 bound_device_id 外键约束），再建 `wheel_aligners` 表，最后用 `ALTER TABLE` 语句补充外键约束（参见 [SQL 第 236-238 行](file:///home/ubuntu/AlignSync/能够生成整个项目的数据库的SQL语句.sql#L236)）。这对应教材第 5 章 5.3 节"参照完整性"中循环引用的处理技巧。

### 5.2 RBAC 多对多权限模型（user_roles + role_permissions）

我采用经典的 RBAC 模型，通过 `user_roles` 和 `role_permissions` 两张关联表实现"用户 - 角色 - 权限"三级多对多关系（参见 [SQL 第 147-164 行](file:///home/ubuntu/AlignSync/能够生成整个项目的数据库的SQL语句.sql#L147)）。这种设计的优势：
- **可扩展**：新增角色或权限不影响已有数据。
- **灵活授权**：一个用户可以同时拥有多个角色，权限取并集。
- **符合教材第 4 章 4.2.5 节"数据库角色"理论**：用角色作为权限的容器，用户通过角色间接获得权限。

### 5.3 JSON 字段存储复合属性（标定数据与功能列表）

我用 JSON 类型存储相机的内参 `intrinsics`（fx/fy/cx/cy/distortion）和外参 `extrinsics`（rotation/translation），以及软件锁的功能列表 `function_list`（参见 [SQL 第 174-175 行](file:///home/ubuntu/AlignSync/能够生成整个项目的数据库的SQL语句.sql#L174) 和 [SQL 第 196 行](file:///home/ubuntu/AlignSync/能够生成整个项目的数据库的SQL语句.sql#L196)）。理由：
- 这些属性是结构化复合属性，传统关系模型拆开会引入大量小表，JOIN 成本高。
- MySQL 8.0 的 JSON 类型支持 `JSON_EXTRACT`、`JSON_CONTAINS` 等函数，可对 JSON 内部字段建索引（虚拟列索引）。
- 对应教材第 7 章 7.3.2 节"复合属性"的处理思想。

### 5.4 冗余字段反范式设计（order_items.product_name/product_model）

`order_items` 表中冗余存储了 `product_name` 和 `product_model`（参见 [SQL 第 271-272 行](file:///home/ubuntu/AlignSync/能够生成整个项目的数据库的SQL语句.sql#L271)），这违反 3NF，但我有意为之：
- **历史快照需求**：产品名称/型号可能被修改，但订单创建时的信息必须冻结，避免历史订单显示错误信息。
- **查询性能**：订单详情查询是高频操作，冗余字段避免每次 JOIN products 表。
- **业务隔离**：即使 products 表中产品被删除（软删除 is_active=0），订单明细仍能展示历史信息。
- 这是典型的"读多写少 + 历史快照"场景下的反范式权衡，符合教材第 7 章 7.4.2 节"数据模型的优化"中"为了查询性能可以适度反范式"的思想。

### 5.5 状态机字段设计

我在所有需要状态流转的表上都设计了 `status` 字段（VARCHAR 字符串枚举），覆盖订单、付款、发货、设备、售后全流程状态流转：
- `purchase_orders.status`: draft → pending → confirmed → awaiting_payment → paid → shipped → completed（或 rejected 分支）
- `payments.status`: awaiting_confirm → confirmed（或 pending_verify / amount_abnormal 分支）
- `shipments.status`: shipped → received
- `cameras.status`: in_stock → used / shipped / returned
- `software_locks.status`: authorized → bound / expired / returned
- `wheel_aligners.status`: assembled → sold / returned
- `after_sales_tickets.status`: pending → processing → resolved → closed（或 rejected 分支）

字符串枚举的优势是可读性好、扩展灵活（新增状态不需要 ALTER TABLE）。这对应教材第 5 章 5.4 节"用户定义的完整性"中 CHECK 约束的思想（MySQL 8.0 已支持 CHECK，但我用应用层校验更灵活）。

## 六、技术难点及解决方案

### 6.1 循环外键依赖（依据第 5 章参照完整性）

**难点**：`software_locks` 与 `wheel_aligners` 互相引用对方的 id 作为外键，但 MySQL 建表时要求被引用表必须先存在，导致两表都无法独立先建。

**理论依据**：教材第 5 章 5.3 节"参照完整性"，循环引用是数据库设计中常见的难题。

**解决方案**：分两步建表 + ALTER 补充约束。
1. 先建 `software_locks` 表（含 `bound_device_id BIGINT` 字段但**不**声明外键）。
2. 再建 `wheel_aligners` 表（声明 `software_lock_id` 外键到 `software_locks.id`）。
3. 最后用 `ALTER TABLE software_locks ADD CONSTRAINT fk_software_locks_bound_device_id_wheel_aligners FOREIGN KEY (bound_device_id) REFERENCES wheel_aligners(id)`（参见 [SQL 第 236-238 行](file:///home/ubuntu/AlignSync/能够生成整个项目的数据库的SQL语句.sql#L236)）。

**佐证**：[SQL 第 236 行](file:///home/ubuntu/AlignSync/能够生成整个项目的数据库的SQL语句.sql#L236) 的 ALTER TABLE 语句。

### 6.2 并发订单号生成（依据第 12 章并发控制）

**难点**：BR-PO-001 要求订单号格式为 `PO+yyyyMMdd+4 位流水`，多用户并发提交订单时如何保证流水号不重复？

**理论依据**：教材第 12 章 12.3 节"封锁"和 12.4 节"封锁协议"。

**解决方案**：用存储过程 `sp_generate_order_no` 在数据库层生成订单号（参见 [SQL 第 533-545 行](file:///home/ubuntu/AlignSync/能够生成整个项目的数据库的SQL语句.sql#L533)），逻辑是：
1. `SELECT MAX(CAST(SUBSTRING(order_no, 11, 4) AS UNSIGNED)) + 1` 取当天最大流水号 + 1。
2. `LPAD(v_seq, 4, '0')` 补零。
3. `CONCAT(v_prefix, v_date_str, ...)` 拼接。

**并发风险与加锁建议**：
- 当前实现存在并发风险——两个事务同时读取 MAX 值，会得到相同的流水号，导致冲突。
- 推荐方案一：在存储过程中对 `purchase_orders` 表加表级写锁（`LOCK TABLES purchase_orders WRITE`），简单但并发性差。
- 推荐方案二：用 `SELECT ... FOR UPDATE` 行锁，但本场景是新建订单，没有具体行可锁。
- 推荐方案三（最佳）：用 MySQL 的 `GET_LOCK('order_no_lock', timeout)` 全局命名锁，或 Redis 分布式锁。
- 在我的应用层（FastAPI + SQLAlchemy），我用 selectinload + 异步事务 + 应用层重试机制来缓解并发冲突。

### 6.3 N+1 查询问题（依据第 10 章查询优化）

**难点**：列表页加载 N 条订单时，如果每条订单都查一次企业名、付款数、发货数，会产生 1 + N 次查询，性能差。

**理论依据**：教材第 10 章 10.2 节"查询优化"和 10.3 节"代数优化"。

**解决方案**：双层优化。
- **数据库层**：用视图 `v_order_summary`（[SQL 第 510-518 行](file:///home/ubuntu/AlignSync/能够生成整个项目的数据库的SQL语句.sql#L510)）封装 JOIN + 子查询，把 N+1 次查询合并为 1 次复杂查询。
- **应用层**：在 SQLAlchemy 中用 `selectinload`（批量 IN 加载）替代默认的 lazy load，避免 ORM 触发 N+1 查询。
- 对应教材第 10 章 10.3.1 节"关系代数表达式等价变换规则"——把"先选择后连接"等价变换为"先连接后选择"，减少中间结果集。

### 6.4 数据隔离（依据第 4 章视图机制）

**难点**：核心技术企业和生产厂各自只能看到自己的数据，比如生产厂 A 不能看到生产厂 B 的订单，但两家企业的部分数据又需要互相可见（如订单双方）。

**理论依据**：教材第 4 章 4.3 节"视图机制"——"视图机制能够把要保密的数据对无权存取这些数据的用户隐藏起来"。

**解决方案**：
- 在视图层加 WHERE 过滤，例如可以创建一个 `v_orders_for_user` 视图，过滤条件是 `WHERE enterprise_id = CURRENT_USER_ENTERPRISE_ID()`。
- 在我的应用层，通过 JWT Token 中的 enterprise_id 在每次查询时自动加 WHERE 过滤。
- 关键表（cameras、software_locks、purchase_orders、after_sales_tickets）都设计了 `enterprise_id` 字段作为数据隔离依据。

### 6.5 批量同步回滚（依据第 11 章事务 ACID）

**难点**：UC-CAM-001 支持批量同步最多 100 个相机，如果第 50 个失败，前 49 个要不要回滚？

**理论依据**：教材第 11 章 11.1 节"事务的基本概念"——事务的 ACID 性质（原子性 Atomicity、一致性 Consistency、隔离性 Isolation、持久性 Durability）。

**解决方案**：采用"逐条回滚 + 容错记录"策略。
- 整个批量同步用一个事务包裹（`BEGIN ... COMMIT/ROLLBACK`）。
- 但对单个相机的同步失败采用 try-catch，记录到 notifications 表，不中断整个事务。
- 这样既保证了"成功部分持久化"（业务需求），又通过 notifications 表实现了"失败部分可追溯"。
- 对应教材第 11 章 11.5 节"恢复策略"中"部分提交 + 日志"的思想。

### 6.6 JSON 数据完整性（依据第 5 章用户定义完整性）

**难点**：JSON 字段（intrinsics、extrinsics、function_list）虽然灵活，但如何保证 JSON 内部结构正确（如 intrinsics 必须包含 fx/fy/cx/cy/distortion 五个字段）？

**理论依据**：教材第 5 章 5.4 节"用户定义的完整性"。

**解决方案**：
- 数据库层用 `JSON NOT NULL` 保证非空，但 MySQL 不支持 JSON Schema 校验。
- 应用层用 Pydantic 模型定义 JSON 结构（如 `CameraIntrinsics` 类包含 fx/fy/cx/cy/distortion 字段），在写入前校验。
- 可选方案：用 MySQL 8.0 的 `JSON_SCHEMA_VALID` 函数（CHECK 约束 + JSON Schema），实现数据库层结构校验。
- 对应教材第 5 章 5.4.1 节"属性上的约束"。

**Q18 [I] 并发订单号生成会不会冲突？怎么解决？**

- **标准回答要点**：当前 `sp_generate_order_no` 用 `SELECT MAX(...)+1` 方案，在并发场景下确实存在冲突风险（两个事务同时读到相同的 MAX 值）。解决方案：(1) **悲观锁**——`LOCK TABLES purchase_orders WRITE` 或 `SELECT ... SET last_seq = last_seq+1` 原子操作获取流水号；(4) **分布式锁**——Redis 分布式锁或 MySQL `GET_LOCK` 全局命名锁。我在应用层采用方案 (2) 乐观重试。

**Q19 [I] 批量同步回滚策略是怎样的？**

- **标准回答要点**：UC-CAM-001 支持批量同步最多 100 个相机。我采用"逐条回滚 + 容错记录"策略：(1) 整个批量同步用一个事务包裹；(2) 单个相机的同步失败采用 try-catch，记录到 notifications 表，不中断事务；(3) 事务结束时统一 COMMIT 成功部分。这样既保证成功部分持久化，又通过 notifications 表记录失败部分便于追溯。对应 ACID 的原子性弱化（部分提交）+ 一致性保证（最终状态正确）。

**Q21 [J] 密码字段为什么不用明文存储？**

- **标准回答要点**：(1) 数据库泄露时明文密码会直接暴露用户隐私；(2) 用 bcrypt 哈希算法（带盐），即使两个用户密码相同，hash 值也不同；(3) bcrypt 计算成本可调（cost factor），抵御彩虹表和暴力破解；(4) `password_hash VARCHAR(255)` 长度 255 容纳 bcrypt 输出（60 字符）+ 算法前缀，未来可扩展到 argon2 等。在 [SQL 第 715 行](file:///home/ubuntu/AlignSync/能够生成整个项目的数据库的SQL语句.sql#L715) 我用了占位字符串 `$2b$12$placeholder_hash_for_123456_demo_only`，真实环境由 passlib bcrypt 生成。
- **理论依据**：教材第 4 章 4.5 节"数据加密"。
- **佐证位置**：[SQL 第 131 行](file:///home/ubuntu/AlignSync/能够生成整个项目的数据库的SQL语句.sql#L131) 与 [SQL 第 715 行](file:///home/ubuntu/AlignSync/能够生成整个项目的数据库的SQL语句.sql#L715)。
